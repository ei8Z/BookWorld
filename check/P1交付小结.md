## 4. 新 CLI 子命令

```bash
bookctl chapter add --volume 2 --chapter 13 --title "第十三章" --pov "林越" [--goal … --status … --word-count … --file-path … --summary …]
bookctl chapter list [--volume 2]

```

均为 `--json` 单行输出，退出码遵循 §5（成功 0 / 参数错 2 / 内部错 1）。
`chapter add` 时若卷不存在会自动建卷，省掉调用方一次建卷操作。

## 5. 设计上的两个取舍（需你知悉）

1. **实体卡逐条裁剪，而不是整分区丢弃。**
   实现过程中发现：若按"分区整体装不下就全丢"，`entities` 分区会被几个在场 NPC 的
   卡片撑爆，结果连 **POV 主角卡**都被一起丢掉。改为实体卡逐条装（顺序即优先级：
   POV → 被提及 → 在场），小预算下也能保住主角。`trimmed` 里会写 `entities` 表示有卡被裁。
2. **在场 NPC 用精简卡，被提及实体才给完整卡。**
   计划只规定"被提及实体取完整卡片"；在场者若也给完整卡（外貌 120 + 性格 80 + 内心 80），
   3 个在场 NPC 就能吃掉 1000+ 字。故在场者只给 名字/身份/状态/好感度。

另外 `build_context` 新增可选参数 `extra_text`，互动模式下把"本轮玩家输入"也算进提及范围
（例如玩家输入"我去找萍萍"能把赵萍拉进上下文）。默认空串，不影响既有调用。

## 8. D12 已解决：`--chapter` 现在真正参与上下文

**修之前的实测**：`--chapter` 是空参——传 1 / 13 / 20 / 不传，输出完全一样（98 字），
只是把值回显到 `chapter` 字段；`chapters` / `scenes` 表里的数据 context 一个字都没读。

**修之后的语义**（计划未规定，按"让 P1 层级真正有用"实现，均受预算约束）：

| 输入 | 效果 |
|---|---|
| `--chapter N` 或 `story_state.chapter` | 读 `chapters` 表取该章 `title/pov/goal` → 渲染 `【本章】第N章 | 标题 | POV：X | 目标：Y` |
| 同上 | 读 `scenes` 表取该章全部 `location` → 渲染 `【本章场景】A、B`，**并把这些地点并入提及匹配范围**（章场景登记了"服务器机房"，同名区域卡就会被带进上下文） |
| `--chapter N`（显式传入） | 未收伏笔只保留 `planted_chapter <= N` 的，**不剧透还没埋的钩子** |
| 不传 `--chapter` | 伏笔**不过滤**，保持既有"列出全部未收伏笔"语义（避免未登记章号的调用方莫名丢伏笔） |
| 超长章标题 / 场景列表 | 与其他分区一样受预算约束，装不下即丢弃并记入 `trimmed`（`chapter` / `chapter_scenes`） |

**实际输出对照**（同一库、同一 POV，只改章号）：
